# slipwai Constitution

slipwai is the factory: a command-line tool that generates repositories carrying the delivery method
(`slipwai generate`), adopts the method into repositories that already exist (`slipwai adopt`,
experimental), and carries both forward to newer factory releases (`slipwai migrate`). It serves whoever runs
it and whoever then works in a repository it made or adopted. Its output is other people's code: a wrong file
lands in a repository the factory no longer controls, and a published version cannot be taken back. What
breaks if this is wrong is every project generated or adopted since the defect shipped, and the one repair
path — a new release, then `slipwai migrate` — works only if the version, the changelog and the migration
path stayed honest. It moves no money, holds no personal data, runs no service and is not event-sourced.

The numbering below is for reference, not priority.

Continuous delivery is how the rest of this document is enforced rather than merely asserted. Two
questions govern every decision below: **why can we not deliver today's work to production today**, and
**what would let us sleep tonight if we did**. Holding both at once is what makes them useful — optimising
either alone produces a system that is fast and unsafe, or safe and irrelevant. Where a CD practice makes
a problem visible, the practice is the diagnostic and the problem was already there; the obligation is to
fix what it found, never to loosen the gate that found it.

The delivery principles below follow [MinimumCD](https://minimumcd.org/minimumcd/) (CC BY-SA 4.0), the
industry-agreed floor for calling a practice continuous delivery, restated for this domain and extended
with the clause on agent-generated change.

**This repository adopted the method; it was not generated by it.** Where a principle is marked a target,
the repository stands below the rung it comes into force at (`delivery/docs/convergence.md`), and what holds
today is written under it. A principle in force binds new code a slice writes; code that was here before is
held to its own recorded commands — `make verify`, and `make -f delivery/Makefile verify` — and to nothing it
did not have before, as `AGENTS.md` says.

## Core Principles

### I. What a Project Was Given Keeps Meaning What It Meant (NON-NEGOTIABLE)

- **An answer a project already gave MUST stay answerable the way it was** until a MAJOR release says
  otherwise. Removing or renaming an axis, an option or a CLI flag, or raising `schemaVersion` in
  `catalog.json`, is a MAJOR; something a project can newly be given is a MINOR; the same answers generated
  better is a PATCH. The one written exemption is the brownfield adoption path (`layout.delivery` in
  `project.json` and everything built on it), which may change in a MINOR only while every place a user meets
  it says it is experimental.
- **A released version is spent.** `v<release>` names exactly the commit whose `VERSION` is that release with
  no suffix; a `v*` tag MUST NOT be moved, a number MUST NOT be reused, and a release MUST be published only
  from the gate run of its own tag once every gate job is green. `make release` is the only thing that writes a
  release into `VERSION`, and `python3 scripts/tag-release.py --dry-run` states what it holds a checkout to.
- **`VERSION` is the one place the number is written**, and the number on `main` MUST be the smallest claim
  the changes since the last release justify: the highest level the `changelog.d/` fragments claim, applied to
  the last released entry. `tests/test_changelog.py` fails when they disagree.
- **Every change that reaches a user MUST carry its fragment in the same commit** — a change under
  `assets/`, `catalog.json`, `src/slipwai/` or the CLI — saying what it changed and what it asks of a
  repository already generated. Where it is unclear whether a change reaches a user, the diff of the tree
  `make starters` materializes before and after is the proof, not a judgement.
- **A generated or adopted project MUST record the factory that made it** in `project.json`'s `generator`,
  so its maintainer can read the changelog against it.
- **Migration MUST be exact.** A project generated at the newest release tag and migrated by the factory at
  `HEAD` MUST be byte-identical to a fresh generation outside the project's own files, and green under its own
  `make verify` (`make test-migration`). An adopted repository migrated from a newer factory MUST come out as
  one clean merge that leaves the repository's own files untouched (`make test-adoption`).
- **Every combination the catalog allows MUST pass its own gate**: the matrix generates each backend's
  variants and runs each one's native `make verify`.

Rationale: a generated repository is somebody else's code the moment it is written. The factory cannot
recall a file, so a defect is repaired only by a later release and a migration — and that repair is only as
good as the version number that announces it, the fragment that says what to do, and the migration that
carries it. A version reused or a MAJOR shipped as a MINOR breaks the repair itself, not just one project.

### II. Re-running Is Safe (NON-NEGOTIABLE)

- `slipwai adopt --refresh` on a tree that has not changed MUST change nothing: the re-survey is a no-op, and
  `make test-adoption` proves it for every fixture.
- `slipwai migrate` MUST replace only the factory's own files — in an adopted repository, those listed in
  `delivery/.written` — and MUST NOT rewrite a file the repository owns.
- `make release` MUST be one atomic push of the release commit, its `v*` tag and the commit that opens the
  next snapshot. A released number MUST NOT be left sitting on `main` unpublished.
- A command a slice adds that writes into a repository MUST be safe to run twice, and a test proving the
  second run changes nothing MUST accompany it.

Rationale: a maintainer re-runs a command when it failed half-way or when they are unsure it ran. Every
repair path this document relies on assumes the second run does no harm.

### III. Simplicity, and the Rung You Are On

- The smallest design satisfying the specification wins. An additional service, cache, queue, broker, or
  abstraction layer MUST be justified in the plan against a named requirement, not against a shape the
  team is used to.
- **How much of the past this system keeps is a plan-time decision, recorded with its reason.** slipwai sits
  on the lowest rung: a command returns its outcome and writes files. The only history it keeps is Git's,
  the changelog, and what `project.json` records, and nothing here asks for more.
- A module MUST NOT be moved up a rung merely for consistency with a neighbour, and moving *down* a rung is
  the harder direction, so a change of rung is recorded as an ADR under the reversal-cost test below.
- The change strategy is `leave-it`: slices land in the existing `slipwai` package under `src/slipwai/`
  (ADR 0002, `Proposed`; decision D2).

Rationale: complexity added for symmetry is the cheapest kind to add and the most expensive kind to
remove, because nothing ever demands its removal.

### IV. Hexagonal Architecture — Domain Isolated from Infrastructure

**A target, not yet in force.** On the *structure* ladder this repository stands at `named`
(`delivery/docs/convergence.md`). This principle comes into force at `hexagonal`; a generated project sits at
`typed`. Until it does, what holds here is written below, and the map's *planned* column names the slice
that climbs.

- Today `src/slipwai/` is one module per part of the repository being generated (`docs/maintaining.md`), not
  domain, application and adapter layers. `make check-structure` already fails a module that imports against
  the declared direction, forms a cycle or outgrows its budget; that is the gate this principle will extend.
- The next rung is `laid-out`, then `hexagonal`. No slice is planned for either: the strategy is `leave-it`
  (ADR 0002, D2), so slices land in the package as it is laid out.

When in force, this principle reads:

> - Domain code MUST NOT import a framework, transport, persistence implementation, clock, UUID generator,
>   vendor SDK, or UI concern. Time and identifiers arrive as typed inputs.
> - **Driving adapters** parse untrusted input into typed commands and call use cases. They hold no
>   business rules and make no authorisation decision.
> - **Driven adapters** implement ports owned by their innermost consumer, injected as parameters.
> - Ports MUST be named for the business conversation, never the technology, and MUST survive an adapter
>   swap. Ports MUST be role interfaces exposing only what the consumer needs.
> - **Every driven port MUST have a usable fake**, written in the test tree, so domain and application
>   layers are testable with no infrastructure running.
> - The dependency direction MUST be enforced by an automated check — in this repository
>   `make check-structure`, extended to the layers — not by reviewer vigilance.

### V. Acceptance-Driven Development from Given-When-Then

<!-- journey: acceptance-driven-testing at tests-exist -->
**A target, not yet in force.** On the *safety net* ladder this repository stands at `tests-exist`
(`delivery/docs/convergence.md`). This principle comes into force at `tests-pass`; a generated project sits at
`mutation-measured`. Until it does, what holds here is written below, and the map's *planned* column names the
slice that climbs.

- Today the suite is recorded (`make test`) and whether it is green in a gate is not established: no workflow
  runs on the fork. New tests stand in at a seam with a fake written in the test tree, never a mocking
  framework (`AGENTS.md`), and a slice's acceptance scenarios enter at the command's boundary — a fixture
  repository surveyed, as `specs/001-rust-cargo-adopt/spec.md` specifies.
- The next rung is `tests-pass`: the suite green in the gate with nothing quarantined. It needs a gate that
  runs on this fork's commits; no slice is planned for it.

When in force, this principle reads:

> - **Level.** Every slice MUST have at least one GWT scenario whose **When** enters through the
>   application's own driving port — **the use case** — and whose **Then** is observable there. A scenario
>   satisfiable by calling an internal function is a unit specification, NOT a slice acceptance criterion.
> - A delivery adapter — here a CLI command — MUST carry a test covering parse, delegate, and the mapping
>   of every outcome to its output and exit status, and MUST NOT be the level at which a rule is proved.
> - **Cycle**: RED-GREEN-REFACTOR, one rule of the example map per increment. Tests written after the code
>   they cover MUST be sent back, and a slice's scenarios MUST NOT be written up front as a batch.
> - **RED is a failing assertion, not a failing build**, and every example MUST be observed failing for its
>   own stated reason before the code that satisfies it is written.
> - REFACTOR is a step, not an option. It happens on green and MUST NOT change observable behaviour.
> - **Behaviour, not structure.** Tests MUST NOT assert private functions, internal call ordering, or mock
>   invocation counts where an observable outcome exists.
> - **One capability per slice, one observable outcome per criterion.**
> - **Evidence gate.** At the end-of-phase point, test effectiveness MUST be evidenced by mutation testing
>   where meaningful, otherwise by recorded reachability, contract, or operational evidence.
> - Bug fixes MUST begin with a boundary-level scenario reproducing the reported behaviour.
> - Coverage percentage is not a gate.

### VI. Contract-Bounded Integrations

- The third-party systems this factory reaches — the package registry, the forge's release API, and the
  sources `make locks` and `scripts/refresh-support.py` read — are reached from the release and maintenance
  scripts under `scripts/` and the Makefile targets that name them. That code is held to its own recorded
  commands.
- An adapter to a third-party system that a slice writes MUST be reached through an interface this codebase
  owns, MUST keep the provider's vocabulary behind it, and MUST have tests against a stub pinned to a
  recorded or published contract, covering each failure mode it maps: a request the caller can fix, a
  rejected credential, rate limiting, a server error, a timeout, and a response the contract does not allow.
- A retry MUST NOT be able to duplicate a non-idempotent effect. Publishing is the case that matters here,
  and the registry accepting a name and version once is what makes a retried publish fail rather than repeat.
- **A stub is not a fake.** A fake implements an interface this codebase owns; a stub impersonates a system
  nobody here owns and is held honest by the contract it is pinned to.

### VII. Observability and Auditability

- slipwai runs no service and no background job, so it keeps no structured logs and owes no correlation
  identifier or heartbeat. If a slice adds a long-running process, logs MUST be structured and carry a
  correlation identifier, and a missing heartbeat MUST be alertable — before that process ships.
- **A command's outcome is its signal.** A refusal MUST go to stderr with a non-zero exit, so a script or a
  gate that runs slipwai detects it without a person reading the output; a zero exit on a failure is a defect.
- **The audit records here are the release record**: `CHANGELOG.md`'s one entry per released version, the
  `v*` tag on the commit it names, and `project.json`'s `generator` in every repository the factory made.
  They are retained for the life of this repository and the registry, and a released entry MUST NOT be
  rewritten.
- A failed publish job MUST fail its run on the forge, which is the alert; a release that did not publish
  MUST NOT look like one that did. No workflow runs on the fork today, so no publish happens from here.
- Personally identifying data — a committer's name or email read from a repository's history — MUST NOT be
  written to `project.json`, the survey page, a report, or anything slipwai prints.

### VIII. Versioning and Breaking Changes

- Published artifacts MUST be versioned MAJOR.MINOR.PATCH, and `main` carries the next release as a
  `.dev<N>` snapshot, a pre-release no installer takes unless asked.
- A breaking change — an answer a project already gave that stops being answerable, or a break in the public
  configuration contract (`catalog.json`, the CLI's flags, what `project.json` records) — MUST ship as a
  MAJOR, and its fragment MUST say what it asks of a repository already generated. A released version stays
  installable, because a released version is never withdrawn; no deprecation window beyond that is set.
- **What a repository records is a contract with every later factory.** Changes to `project.json` and to
  `catalog.json` MUST be additive, readers MUST tolerate unknown fields, and removing or retyping a field
  requires a new `schemaVersion` or `schema` number and a path that carries old records forward.
- `slipwai migrate` MUST stay backward compatible with every repository generated or adopted by an earlier
  release: a repository made at the newest release tag migrates to `HEAD` as `make test-migration` requires.
- A change under the experimental exemption still writes its catch-up note, so `migrate` carries an adopted
  repository forward like any other.

### IX. Security, Privacy, and Compliance

- Secrets MUST come from the environment or a secret manager: the registry and forge tokens the publish
  jobs use arrive as the forge's secrets, and `make publish-wheel` and `make publish-release` read them from
  the environment. A committed secret is a build-breaking failure.
- A credential MUST NOT be logged — not by the CLI, a script, or a workflow step — and MUST NOT enter a file
  the factory generates or a repository it adopts.
- slipwai holds no personal data, card data or regulated records, and processes none; there is no
  compliance scope to keep minimal and no right to erasure to design for. A slice that would introduce any
  MUST stop and ask, and its classification and erasure mechanism is an ADR before the first record is kept.
- Nothing here is served, so there is no request to authorise and no tenant to separate.
- Dependencies are not scanned in the gate today (`commands.audit` is null). Once an audit command is
  recorded — the Platform row's `audited` rung — a known-exploitable critical finding blocks release.

### X. Continuous Integration on Trunk (NON-NEGOTIABLE)

Integration here stands at `trunk`, confirmed: pull-request branches mostly merged within an hour. Trunk is
`main` on the fork `mbonnic-psx/Slippy`; nothing is integrated upstream from this repository. The next rung,
`continuous`, needs CI on every commit on this forge, and no workflow runs on the fork today — so the build
that stops the line is `make verify` and `make -f delivery/Makefile verify`, run before every push.

- Every engineer MUST integrate to trunk at least once per day. Work that has not reached trunk is
  unintegrated no matter how often a build ran against the branch it sits on.
- Where branches are used they MUST be cut from trunk, MUST re-integrate to trunk, and MUST live less than
  a day. Long-lived `develop`, integration, or per-feature branches MUST NOT exist.
- Trunk MUST be releasable at every commit. **A red trunk stops the line**: while the build is failing the
  only permitted work is restoring it, and a failure MUST NOT be carried into a later change.
- A work item MUST be codeable, testable, reviewable, and integrable within **two days**. An item that is
  not MUST be split before it is started. One pull request per slice, and the adoption commit merged alone.
- Fixes MUST travel forward through trunk. Cherry-picking a change onto a release branch MUST NOT be the
  route to production.
- **A stack of dependent pull requests is a symptom, not a technique.** Where one is used it MUST name
  whether it compensates for work never decomposed into shippable slices or for review latency, and MUST be
  treated as temporary.

Rationale: batch size is the variable every other guarantee here depends on. A 566-file pull request of five
slices was reviewed by nobody, and a framework's major version moved inside it unseen.

### XI. One Path to Production, and the Pipeline Decides (NON-NEGOTIABLE)

<!-- journey: one-path-to-production at pipeline -->
**A target, not yet in force.** On the *path to production* ladder this repository stands at `pipeline`
(`delivery/docs/convergence.md`). This principle comes into force at `one-path`; a generated project sits at
`pipeline-decides`. Until it does, what holds here is written below, and the map's *planned* column names the
slice that climbs.

- Today `verify.yml` publishes the snapshot on every green push to `main` and the release when its `v*` tag's
  run is green, gated on every job. Beside it, `release.yml`, `package.yml` and `publish-package.yml` run by
  hand, and `make publish-wheel` and `make publish-release` can publish from a checkout with a token in the
  environment — more than one route. No workflow runs on the fork, and the owner brief reserves cutting a
  release and publishing to a person.
- The next rung is `one-path`: every route but one retired or folded into it. No slice is planned for it.

When in force, this principle reads:

> - Exactly **one** automated pipeline MUST deliver every change to every environment. Hotfixes, rollbacks,
>   configuration changes, and emergency work use it too. A second route, even one used once, invalidates
>   every claim the first route makes.
> - **The pipeline is the release authority.** If it passes, the artifact is deployable; if it fails, it is
>   not. A human MUST NOT be able to override the verdict, and a passing pipeline MUST NOT require a further
>   sign-off to proceed.
> - The Definition of Deployable MUST be automated in full and identical for every environment. In this
>   repository it is what `make verify` and `make -f delivery/Makefile verify` run.
> - Everything the pipeline consumes MUST be in version control — source, pipeline definition, the runner
>   image and its pinned versions, tool and runtime versions, and dependency locks. Floating versions MUST NOT
>   appear anywhere the pipeline reads. If a change can be made without a commit, that thing is not managed.
> - Every pipeline step MUST be runnable locally by the same command CI runs.
> - **Flaky tests are defects, not weather.** A test that passes and fails on the same commit MUST be fixed,
>   quarantined, or deleted the day it is noticed. Re-running a build to obtain a pass is prohibited.

### XII. Build Once, Deploy Anywhere; Deploy Is Not Release

<!-- journey: build-once-deploy-is-not-release at pipeline -->
**A target, not yet in force.** On the *path to production* ladder this repository stands at `pipeline`
(`delivery/docs/convergence.md`). This principle comes into force at `pipeline-decides`; a generated project
sits at `pipeline-decides`. Until it does, what holds here is written below, and the map's *planned* column
names the slice that climbs.

- Today the wheel and the executable are built in CI, and a released version is published once: the registry
  accepts a name and version once and a `v*` tag never moves. Snapshots are published as pre-releases on
  every green push to `main`, and the `snapshot` tag is remade each time. There is no environment to promote
  through, no release flag and no rollback: a bad release is superseded by a new one, never withdrawn.
- The next rung is `pipeline-decides`, after `one-path`. No slice is planned for it.

When in force, this principle reads:

> - One artifact MUST be built once per commit and promoted unchanged through every environment.
>   Rebuilding per environment discards the evidence the pipeline produced and MUST NOT happen.
> - Artifact identity MUST be unique and immutable. Snapshot versions and mutable tags MUST NOT be deployed.
> - Configuration that varies between environments MUST come from the environment; configuration that does
>   not vary MUST ship inside the artifact and be tested with it.
> - **Deployment and release are separate decisions.** Incomplete work reaches production dark, behind a
>   flag, and every release flag MUST have an owner, a removal date and tests on both paths, and MUST be
>   removed once the rollout completes, within a lifetime agreed when this principle comes into force.
> - **Rollback MUST be a single automated action**, executable by anyone on the team without approval,
>   within a time agreed when this principle comes into force, and exercised on a routine schedule.
> - Schema change MUST follow expand/contract across separate deployments; an additive and a destructive
>   step MUST NOT ship in the same deployment.

### XIII. Fast Feedback, or It Is Not Feedback

<!-- journey: fast-feedback at tests-exist -->
**A target, not yet in force.** On the *safety net* ladder this repository stands at `tests-exist`
(`delivery/docs/convergence.md`). This principle comes into force at `fast`; a generated project sits at
`mutation-measured`. Until it does, what holds here is written below, and the map's *planned* column names the
slice that climbs.

- Today `make verify` is one command, locally and in CI, and `make test TESTS=...` runs a slice of it. No
  feedback budget is measured or gated. The matrix generates every backend's projects and runs each one's own
  gate, so it needs every toolchain present, and installing a generated project's packages reaches the
  network.
- The next rung is `fast`, after `tests-pass`. No slice is planned for it.

When in force, this principle reads:

> - Feedback budgets, each a gate on the suite rather than an aspiration: unit tests in watch **under one
>   second**; the pre-push deterministic set **under two minutes**; the full deterministic pre-merge suite
>   **under ten minutes**. Exceeding a budget is a defect in the suite — fix the suite.
> - The deterministic suite MUST NOT depend on any system the team does not control: no live third-party
>   calls, no shared mutable environment, no ordering between tests, no wall-clock sleeps.
> - Test doubles used in the deterministic suite MUST be validated against the real system by contract tests
>   that run outside it.
> - **Test changes MUST ship in the same commit as the code they cover.**
> - Non-deterministic checks — end-to-end smoke, load, resilience, exploratory testing — run after deploy.
>   They MUST NOT gate merge.
> - A problem in what was published MUST be detected by alerting within a target agreed when this principle
>   comes into force, not by a user.

### XIV. Agent-Generated Change Meets the Same Bar (NON-NEGOTIABLE)

- An agent-generated change MUST clear the same pipeline and the same Definition of Deployable as a
  human-generated one. There MUST NOT be a fast lane for agent output, and there MUST NOT be an extra
  manual gate applied to it because of its origin.
- **Humans own intent.** The specification, the acceptance criteria, the architectural constraints, and
  this constitution are human-authored and human-amended. An agent MUST NOT edit them to make its own
  change pass. Where they conflict with an implementation, they win. This version was drafted by `/cruise`
  and holds until a person reviews it; a person's amendment wins over it.
- Every change MUST carry its intent as versioned artifacts delivered in the same commit as the code: the
  problem being solved, the observable behaviour as GWT scenarios, the constraints, and the acceptance
  criteria — `specs/<feature>/` and, for a user-visible change, its `changelog.d/` fragment.
- **One scenario, one session, one commit.** An agent session MUST be scoped to a single acceptance
  scenario and MUST end at a green commit. While the build is red, the only permitted agent work is
  restoring it.
- An agent MUST stop and ask when a decision falls outside its constraints — **a name in the domain
  vocabulary, a field `project.json` or `catalog.json` records, a new dependency, or a change to a published
  contract**. Guessing to keep moving is prohibited. Under `/cruise` the question goes to the product owner's
  delegate, which decides as `.specify/product-owner.md` directs and records each answer in
  `specs/<feature>/decisions.md`; a fact nobody here has parks for a person.
- Merging a pull request, cutting a release, publishing a package, and anything aimed at the upstream
  repository are a person's, always.
- Review of agent-written code MUST examine intent alignment, architectural conformance, and complexity.
  "The tests pass" is the pipeline's finding, not the reviewer's. No automated reviewer replaces the person
  who merges.

Rationale: an agent cannot silently route around a vague specification, an unreliable suite, or a coupled
architecture the way an experienced engineer does without noticing. Agentic delivery does not create these
weaknesses; it removes the human compensation that was concealing them.

> - Types, functions, modules, tests, and user-facing copy MUST use that vocabulary. A technical synonym

> - Domain concepts MUST be modelled as types rather than primitives, so one identifier cannot be passed

> - **Constructors MUST make illegal states unrepresentable.** Untrusted input is parsed into a valid domain
>   type once, at the boundary; code past that point MUST NOT re-validate the same primitive.

## Additional Constraints

- All timestamps and dates slipwai records MUST be UTC, in ISO 8601.
- What a repository records MUST be facts true on any machine. Runtime context — absolute file paths,
  hostnames, user names, process ids — MUST NOT appear in `project.json` or anything else the factory writes.
- `VERSION` is the only place this factory's version is written; files under `release/` are build outputs
  and MUST NOT be edited, and neither may anything listed in `delivery/.written`.
- Simplicity governs, per III: the smallest design satisfying the spec wins.

### Technology Stack

- Python 3.11, pinned as the recorded toolchain and as mypy's target, and baked with every backend
  toolchain into the CI runner image pinned in `.github/runner/versions.env`. Development tools — ruff and
  mypy — are pinned in `requirements-dev.txt`, at the versions a generated Python project is given. A pin
  nobody can satisfy is worse than no pin: change it by upgrading environments, not by editing the pin.

When in force, this principle reads:

> - Strict type checking MUST be enabled at its maximum practical setting.
> - Escape hatches (`Any`, a bare `type: ignore`) MUST NOT appear in domain or application code. Untyped
>   external data enters as `object` or `unknown` and is narrowed by a runtime schema.
> - **Schema-first at trust boundaries.** Every crossing MUST be validated by a runtime schema: inbound
>   requests, third-party responses, and anything read back out of storage — `project.json` included —
>   because stored data outlives the code that wrote it.

## Development Workflow and Quality Gates

- Every plan MUST include a Constitution Check naming which principles the feature touches, which rung it
  sits on per III, and how it complies.
- Every pull request MUST pass `make verify` (lint, typecheck, structure, tests) and
  `make -f delivery/Makefile verify`, including at least one boundary-level scenario per slice, and MUST be
  reviewed by an engineer who did not write the change; pair or ensemble programming satisfies the review
  obligation without a separate step. While no workflow runs on the fork, both run locally before the push.
- A pull request MUST NOT be merged while the gate is red, and MUST NOT be merged by disabling a gate.
- **Review is a flow constraint, not a queue.** No review SLA is agreed here; a pull request waiting longer
  than a working day MUST be escalated to the owner rather than tolerated.
- A pull request SHOULD change fewer than 200 lines, and MUST carry one slice.
- Formatting and style MUST be enforced by tooling — ruff here. A review comment about style is a missing
  lint rule.
- A change touching the release path — `VERSION`, `changelog.d/`, `scripts/tag-release.py`, the publish
  jobs, `catalog.json`'s `schemaVersion` — MUST be reviewed with the release rules of I in front of the
  reviewer, and is merged by a person.
- Deviations from a principle MUST be recorded in the pull request under a "Complexity / Deviation"
  heading, naming the principle and the reason. Silent deviation is a defect.
- Where a slice is delivered with stubs, the stubs and their consequences MUST be recorded explicitly.
- **A decision that would cost a migration to reverse MUST be recorded as an ADR** in `delivery/docs/adr/`,
  using Nygard's five sections (Title, Status, Context, Decision, Consequences). The test is reversal cost,
  not importance: stored data must change shape, a repository already generated must be migrated, a contract
  must be versioned, or history would have to be rewritten. The change strategy, a new runtime dependency, a
  field `project.json` or `catalog.json` records, and a CLI flag always qualify. **An accepted ADR MUST NOT
  be edited**; a decision is changed by a new ADR that supersedes it, with links resolving in both
  directions. An ADR drafted by an agent MUST start at `Proposed` — accepting an architecture decision is a
  human act. A slice-scoped design decision stays in that slice's `research.md`, and MUST be promoted to an
  ADR when it turns out to outlive its slice.

## Governance

This constitution supersedes other development practices in this project. Where a style guide, template,
skill, or prior decision conflicts with it, this document wins — save that `AGENTS.md`'s versioning rules are
restated in I rather than overridden, and where the two ever differ, the difference is a defect to amend here.

**Amendment procedure.** Amendments MUST be proposed as a pull request modifying this file on the fork,
MUST state the rationale and the version bump with its justification, and MUST be approved and merged by a
person. Amendments invalidating existing code MUST include a migration plan. A principle moving from target
to in force follows its axis on the convergence map, and is written in full in the same change that records
the rung.

**Versioning policy.** MAJOR — a principle removed or redefined such that compliant work would now
violate it. MINOR — a principle or section added, or guidance materially expanded. PATCH —
clarification changing no obligation. This number is the constitution's, not the factory's `VERSION`.

**Compliance review.** Every review MUST verify compliance with the principles the change touches, and
`make -f delivery/Makefile check-constitution` holds the floor. Maintainers MUST review this constitution
against actual practice at least quarterly; a principle routinely ignored MUST be enforced or amended away,
never left as decoration.
